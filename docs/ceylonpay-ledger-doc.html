How Spring Boot thinks

Every part below leans on the same handful of ideas. Get these straight once and the rest of the codebase reads as applications of them, not new tricks.

Inversion of Control & Dependency Injection

In plain Java, a class that needs a collaborator constructs it: new UserRepository(). That wires your class to one concrete way of building that collaborator, forever. Spring flips this: you declare what you need in a constructor, and a container — the ApplicationContext — builds every object graph for you at startup and hands the dependency in. You never call new on your own services.

Theory
This is Inversion of Control: control over object creation moves from your code to the framework. Dependency Injection is the mechanism — Spring reads your constructor's parameter types, finds a matching bean (an object it manages), and passes it in.
TransferService.java
public TransferService(UserRepository userRepository, WalletRepository walletRepository,
                        TransactionRepository transactionRepository, AuditLogRepository auditLogRepository) {
    this.userRepository = userRepository;
    this.walletRepository = walletRepository;
    this.transactionRepository = transactionRepository;
    this.auditLogRepository = auditLogRepository;
}

Every service and controller in this project uses constructor injection like this — final fields, no @Autowired anywhere. That's a deliberate, slightly old-fashioned-looking choice: a class that can't compile without its dependencies can't silently run half-wired, and the constructor signature is the class's dependency list — no need to open the body to find out what it needs. Field injection (@Autowired private Foo foo;) is the shortcut you'll see in older tutorials; it works, but it hides the dependency list and makes the class impossible to construct without Spring.

What a "bean" actually is

A bean is just an object whose lifecycle Spring owns. Three ways this project creates them:

  • @Service, @RestController, @Component on a class — Spring finds it during classpath scanning (triggered by @SpringBootApplication on CeylonPayApplication) and constructs one instance.
  • @Bean methods inside an @Configuration class — for objects you don't own the source of, or that need custom construction logic. SecurityConfig uses this for PasswordEncoder and CorsConfigurationSource.
  • Interfaces extending JpaRepository — Spring Data generates an implementation and registers it as a bean at startup. You never write a repository class body.

Unless stated otherwise, a bean is a singleton — one instance, shared by everything that asks for it, for the life of the application. That's safe here because none of these services hold mutable state on the instance itself; every request's data lives in method parameters and the database, not in fields.

01

Foundation — entities, JPA, Postgres

User · Wallet · JPA/Hibernate

Part 1 does one job: give the rest of the app a database to talk to, through Java objects instead of raw SQL.

JPA & Hibernate, in one paragraph

Theory
JPA (Jakarta Persistence API) is a specification: a set of annotations and interfaces for mapping Java objects to relational tables — @Entity, @Id, @Column, and so on. Hibernate is the library that actually implements the spec: it reads those annotations, generates SQL, and turns result sets back into objects. Spring Boot wires the two together and adds Spring Data JPA on top, which can write your repository queries for you from a method name alone.
entity/User.java
@Entity
@Table(name = "users")
@Getter @Setter @NoArgsConstructor @AllArgsConstructor
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private String id;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false, unique = true)
    private String phone;

    // nic, password, role...

    @CreationTimestamp
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;
}

Three choices here are worth being able to defend out loud:

  • String UUID primary keys instead of an auto-incrementing Long. GenerationType.UUID asks Hibernate to generate a random UUID in Java before insert. For anything money-adjacent, sequential integer IDs leak information (row count, ordering, "guess the next ID") — a UUID doesn't.
  • @CreationTimestamp / @UpdateTimestamp (on Wallet) are Hibernate's annotations, not JPA's — Hibernate sets the field itself at insert/update time, so no service code ever has to remember to stamp a timestamp.
  • Lombok (@Getter @Setter @NoArgsConstructor @AllArgsConstructor) generates the boilerplate getters/setters/constructors at compile time via an annotation processor. Look at pom.xml: it's marked <optional>true</optional> and explicitly excluded from the Spring Boot Maven plugin's packaging step — it only needs to exist while compiling, never in the shipped jar.

Money is a BigDecimal, never a float

Theory
float/double are binary floating point — they cannot represent most decimal fractions exactly (0.1 in binary is a repeating fraction), which is exactly the kind of rounding error a ledger cannot tolerate. BigDecimal stores an exact, arbitrary-precision decimal.

Wallet.balance and Transaction.amount are both declared @Column(precision = 19, scale = 4) — up to 19 total digits, 4 of them after the decimal point, matched exactly by the column type Postgres creates (numeric(19,4)). The Java type and the database type agree on precision; nothing gets silently truncated on either side.

Repositories: queries from method names

repository/WalletRepository.java
public interface WalletRepository extends JpaRepository<Wallet, String> {
    Optional<Wallet> findByUserId(String userId);
}

No SQL, no implementation — Spring Data parses the method name at startup (findBy + UserId) and generates a query against the user property of Wallet. TransactionRepository takes this further with findBySender_IdOrReceiver_IdOrderByCreatedAtDesc — the underscore tells Spring Data to cross the sender relationship and match its id, rather than looking for a flat property literally named sender_Id.

02

Authentication — JWT & Spring Security

AuthService · JwtUtil · JwtAuthFilter · SecurityConfig

This is the part interviewers probe hardest, because it's where "I copied a tutorial" and "I understand the filter chain" sound completely different.

Why tokens, not sessions

Theory
A traditional server keeps a session in memory (or a shared store) per logged-in user, and gives the browser a session-id cookie to look it up on every request. That means the server has to remember state, and remembering state across multiple server instances needs a shared session store. A JWT (JSON Web Token) flips this: the token itself carries everything the server needs to trust the caller, cryptographically signed so it can't be forged. The server verifies a signature instead of looking anything up — stateless. That's why SecurityConfig sets SessionCreationPolicy.STATELESS: Spring is told not to create an HttpSession at all.

A JWT has three dot-separated, Base64URL-encoded parts: a header (algorithm used), a payload (claims — here just the user's ID, issued-at, and expiry), and a signature (HMAC-SHA of the first two parts, computed with a secret key only the server knows). Anyone can read the payload — it's just Base64, not encrypted — but nobody can alter it without invalidating the signature.

security/JwtUtil.java
public JwtUtil(@Value("${jwt.secret}") String secret,
                @Value("${jwt.expiration-ms}") long expirationMs) {
    this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));
    this.expirationMs = expirationMs;
}

public String generateToken(String userId) {
    Date now = new Date();
    return Jwts.builder()
            .subject(userId)
            .issuedAt(now)
            .expiration(new Date(now.getTime() + expirationMs))
            .signWith(key)
            .compact();
}

@Value("${jwt.secret}") pulls the signing key from application.properties (or, in production, the JWT_SECRET environment variable via the docker profile) rather than hardcoding it — the same secret has to sign and later verify every token, so it must never change while tokens are still valid, and never leak. The token's subject is just the user's UUID — deliberately minimal. No name, no phone, no role: anything sensitive stays in the database, looked up fresh on each request that needs it.

Flow: register & login

sequenceDiagram
    participant C as Browser
    participant AC as AuthController
    participant AS as AuthService
    participant DB as Postgres
    participant JU as JwtUtil

    C->>AC: POST /api/auth/register {name, phone, nic, password}
    AC->>AS: register(request)
    AS->>DB: findByPhone / findByNic
    DB-->>AS: not found
    AS->>AS: passwordEncoder.encode(password)
    AS->>DB: save User, save Wallet(balance = 0)
    AS->>JU: generateToken(user.id)
    JU-->>AS: signed JWT
    AS-->>AC: AuthResponse(token, userId, name)
    AC-->>C: 200 OK + JWT

    Note over C,DB: Later — logging back in
    C->>AC: POST /api/auth/login {phone, password}
    AC->>AS: login(request)
    AS->>DB: findByPhone(phone)
    DB-->>AS: User (hashed password)
    AS->>AS: passwordEncoder.matches(raw, hashed)
    AS->>JU: generateToken(user.id)
    JU-->>AS: signed JWT
    AS-->>AC: AuthResponse
    AC-->>C: 200 OK + JWT

Both endpoints end the same way — a fresh signed JWT — but only login checks a password. Registration trusts the request because it's creating a brand-new identity; there's nothing to authenticate against yet.

In this codebase
Registration creates two rows in one call — a User and a zero-balance Wallet — so it's structurally impossible to have a user with no wallet. Passwords are hashed with BCryptPasswordEncoder (a PasswordEncoder bean from SecurityConfig): a slow, salted, one-way hash — matches() re-hashes the login attempt with the same embedded salt and compares, the raw password is never stored or compared directly.

Flow: an authenticated request & the filter chain

Theory
Spring Security works as a chain of servlet filters that every HTTP request passes through before it reaches your @RestController. Each filter can inspect the request, reject it outright, or attach information for the next one. SecurityFilterChain is where you declare which filters run and in what order.
sequenceDiagram
    participant C as Browser
    participant JF as JwtAuthFilter
    participant SC as SecurityContextHolder
    participant TC as TransferController
    participant TS as TransferService

    C->>JF: POST /api/transfer
Authorization: Bearer <jwt>
    JF->>JF: isTokenValid(token)?
    alt token valid
        JF->>JF: extractUserId(token)
        JF->>SC: setAuthentication(userId, no roles)
        JF->>TC: filterChain.doFilter(...)
        TC->>TS: transfer(authentication.getName(), ...)
        TS-->>TC: TransactionResponse
        TC-->>C: 200 OK
    else missing / invalid token
        JF->>TC: filterChain.doFilter(...) (no Authentication set)
        TC->>C: 401 Unauthorized (AuthenticationEntryPoint)
    end

The controller never touches the JWT directly. By the time TransferController runs, Spring has already resolved who is calling — it just reads Authentication.getName().

security/JwtAuthFilter.java
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                 FilterChain filterChain) throws ServletException, IOException {
    String header = request.getHeader("Authorization");
    if (header != null && header.startsWith("Bearer ")) {
        String token = header.substring("Bearer ".length());
        if (jwtUtil.isTokenValid(token)) {
            String userId = jwtUtil.extractUserId(token);
            var authentication = new UsernamePasswordAuthenticationToken(userId, null, Collections.emptyList());
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }
    }
    filterChain.doFilter(request, response); // always continue — Security decides authorized-ness later
}

JwtAuthFilter extends OncePerRequestFilter — a Spring Security base class that guarantees the filter's logic runs exactly once per request, even across internal forwards. It's registered via .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class) in SecurityConfig — inserted just ahead of Spring Security's own username/password filter, so JWT authentication happens before Spring gets a chance to look for anything else.

Theory
The neat trick: new UsernamePasswordAuthenticationToken(userId, null, emptyList()) puts the raw userId string in as the principal (first argument). When something later calls authentication.getName(), Spring Security calls toString() on the principal — since it's already a String, that's just the user's UUID. No custom UserDetails class needed; every controller in this project fetches "who is calling" with one line: authentication.getName().

Notice the third argument is an empty authorities list — no roles are granted. That's fine here because SecurityConfig only distinguishes "authenticated" from "not authenticated" (anyRequest().authenticated()), never role-based access — every logged-in user can call every non-auth endpoint, and per-user data isolation is enforced in the service layer instead (see Part 3).

The security filter chain, declared

config/SecurityConfig.java
http
    .cors(cors -> cors.configurationSource(corsConfigurationSource()))
    .csrf(csrf -> csrf.disable())
    .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .requestMatchers("/error").permitAll()
            .anyRequest().authenticated()
    )
    .exceptionHandling(ex -> ex.authenticationEntryPoint((req, res, e) ->
            res.sendError(HttpServletResponse.SC_UNAUTHORIZED, "Unauthorized")))
    .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
  • CSRF is disabled — Cross-Site Request Forgery protection defends cookie-based sessions, where a browser attaches cookies automatically to any site's request. A stateless, header-based JWT API has nothing for CSRF to exploit: no ambient cookie, no automatic attachment.
  • /api/auth/** is permitAll() — you can't require a JWT to obtain a JWT. Everything else falls to anyRequest().authenticated().
  • The custom authenticationEntryPoint overrides Spring's default (a login-page redirect, meaningless for a JSON API) with a plain 401.
03

Wallet & deposit — access control without roles

WalletService · WalletController

There's no @PreAuthorize or role check anywhere in WalletController. So what stops User A from reading User B's balance?

Theory
This is resource-based access control: instead of asking "is this role allowed to call this endpoint", the service asks "does the resource being fetched belong to the caller". Both questions are "authorization", but the second one is enforced by the query itself, not a separate rule engine.
service/WalletService.java
public BalanceResponse getBalance(String userId) {
    Wallet wallet = walletRepository.findByUserId(userId)
            .orElseThrow(() -> new WalletNotFoundException("No wallet found for this user"));
    return toResponse(wallet);
}

WalletController.getBalance(Authentication authentication) passes authentication.getName() — the JWT-derived userId, never a client-supplied one — straight into this lookup. There is no endpoint that takes a wallet ID or user ID as a request parameter; the only wallet a request can ever touch is the caller's own, because the query is always scoped by the identity the filter chain already verified. The access control isn't a check you could forget to add — it's the shape of the query.

P2P transfer — the correctness centerpiece

TransferService · @Transactional

A transfer touches two wallets, a transaction record, and an audit log. If any step fails partway, money must not appear or vanish. This is the one part of the app where getting the theory wrong means losing (or duplicating) real money.

ACID, and which letter @Transactional buys you

Theory
A database transaction is judged against four properties — Atomicity (all-or-nothing), Consistency (never leaves data in a state that violates its rules), Isolation (concurrent transactions don't see each other's half-finished work), Durability (once committed, survives a crash). Spring's @Transactional wraps a method in a proxy: it opens a database transaction before the method runs, and — this is the important part — rolls the whole thing back if the method exits via an unchecked (RuntimeException) exception, or commits it if the method returns normally.
service/TransferService.java
@Transactional
public TransactionResponse transfer(String senderUserId, String toPhone, BigDecimal amount) {
    Wallet senderWallet = walletRepository.findByUserId(senderUserId)
            .orElseThrow(() -> new WalletNotFoundException("Sender wallet not found"));
    // ...look up recipient, reject self-transfer...

    if (senderWallet.getBalance().compareTo(amount) < 0) {
        throw new InsufficientBalanceException("Insufficient balance");  // ← rolls back everything below
    }

    senderWallet.setBalance(senderWallet.getBalance().subtract(amount));
    recipientWallet.setBalance(recipientWallet.getBalance().add(amount));
    walletRepository.save(senderWallet);
    walletRepository.save(recipientWallet);

    Transaction txn = new Transaction(senderWallet, recipientWallet, amount, "SUCCESS");
    transactionRepository.saveAndFlush(txn);
    auditLogRepository.save(new AuditLog(txn, buildAuditDetail(senderWallet, recipientWallet, amount)));

    return new TransactionResponse(txn.getId(), amount, toPhone, senderWallet.getBalance(), txn.getCreatedAt());
}

Notice the balance check happens before either wallet is mutated — that's just good order, not what makes this safe. What makes it safe is that InsufficientBalanceException, WalletNotFoundException, and InvalidTransferException are all unchecked exceptions extending RuntimeException. If the balance check fails, throwing is enough — Spring's transactional proxy catches it, issues a database ROLLBACK, and neither wallet's `save()` (which, at that point, hasn't even been called) ever reaches the database. If you moved the balance mutation earlier and the check later, atomicity would still save you — that's the property's whole point.

sequenceDiagram
    participant C as Client
    participant TC as TransferController
    participant TS as TransferService (@Transactional)
    participant DB as Postgres

    C->>TC: POST /api/transfer {toPhone, amount}
    TC->>TS: transfer(senderId, toPhone, amount)
    TS->>DB: BEGIN
    TS->>DB: find sender wallet, recipient wallet
    alt sender == recipient
        TS-->>TC: throw InvalidTransferException
        TS->>DB: ROLLBACK
        TC-->>C: 400 "Cannot transfer to your own wallet"
    else balance too low
        TS-->>TC: throw InsufficientBalanceException
        TS->>DB: ROLLBACK
        TC-->>C: 400 "Insufficient balance"
    else balance sufficient
        TS->>DB: UPDATE sender.balance -= amount
        TS->>DB: UPDATE recipient.balance += amount
        TS->>DB: INSERT Transaction, flush
        TS->>DB: INSERT AuditLog
        TS->>DB: COMMIT
        TS-->>TC: TransactionResponse
        TC-->>C: 200 OK
    end

Two failure branches, one success branch — every branch either commits a fully-consistent pair of balances, or rolls back to the state before the transaction started. There's no branch that leaves one wallet updated and the other not.

Why saveAndFlush, not save
Plain save() can defer the actual SQL INSERT until the transaction commits (Hibernate batches writes for efficiency). saveAndFlush() forces that INSERT to run immediately, so txn.getId() and txn.getCreatedAt() — both database-generated — are guaranteed populated in time to build the AuditLog and the response, still inside the same transaction.

Reading history: the counterparty view

getHistory deliberately isn't @Transactional — it only reads, and a plain read doesn't need atomicity or a rollback path. The interesting bit is how one row becomes "sent" for one wallet and "received" for the other, from the exact same stored Transaction:

service/TransferService.java
private TransactionHistoryResponse toHistoryResponse(Transaction txn, String myWalletId) {
    boolean sent = txn.getSender().getId().equals(myWalletId);
    Wallet counterparty = sent ? txn.getReceiver() : txn.getSender();
    return new TransactionHistoryResponse(
            txn.getId(), sent ? "SENT" : "RECEIVED",
            counterparty.getUser().getName(), counterparty.getUser().getPhone(),
            txn.getAmount(), txn.getCreatedAt());
}

One immutable row, two viewpoints — the direction label is computed relative to whoever is asking, never stored on the row itself. Storing "SENT"/"RECEIVED" on the transaction would mean storing it twice (once per party) or picking one party's viewpoint arbitrarily; deriving it keeps the row a single source of truth.

Testing & Docker

Mockito · @SpringBootTest · multi-stage build

Two different things both called "testing"

Theory
A unit test isolates one class by replacing its collaborators with fakes, so a failure points at exactly one place and the test runs in milliseconds with no external system. An integration test boots real (or realistic) collaborators — a real Spring context, a real database — to prove the wiring between classes actually works, at the cost of being slower and telling you less precisely where a failure lives.
service/TransferServiceTest.java — unit test
@ExtendWith(MockitoExtension.class)
class TransferServiceTest {
    @Mock private WalletRepository walletRepository; // fake — never touches a database
    @InjectMocks private TransferService transferService; // real object, fakes wired in

    @Test
    void transfer_shouldThrow_whenBalanceInsufficient() {
        // given two mocked wallets...
        assertThatThrownBy(() -> transferService.transfer("user-sender", "0722222222", new BigDecimal("200.00")))
                .isInstanceOf(InsufficientBalanceException.class);

        verify(walletRepository, never()).save(any()); // proves nothing was persisted
    }
}

@Mock creates a fake WalletRepository that returns exactly what a when(...).thenReturn(...) stub tells it to; @InjectMocks constructs a real TransferService with those fakes wired into its constructor. No Spring context boots, no database connects — this whole test suite runs in well under a second, which is why the project has seven unit tests exercising every branch of transfer() and getHistory() individually.

TransferIntegrationTest.java — integration test
@SpringBootTest
@AutoConfigureMockMvc
class TransferIntegrationTest {
    @Autowired private MockMvc mockMvc; // drives real HTTP request handling, no real socket

    @Test
    void transferMovesRealMoneyBetweenRealWalletsThroughTheFullStack() throws Exception {
        String senderToken = register("Sender E", SENDER_PHONE, "555555555V", "passwordE");
        // deposit, then transfer, through real controllers, real services, a real Postgres
        assertThat(senderWallet.getBalance()).isEqualByComparingTo("300.0000");
    }
}

@SpringBootTest boots the entire application context — every bean, real database connection, the works. @AutoConfigureMockMvc lets the test drive HTTP requests (mockMvc.perform(post(...))) through the actual DispatcherServlet routing, security filters included, without opening a real network port. This single test proves AuthController → AuthService → TransferController → TransferService → repositories → Postgres all agree with each other — something no amount of mocking could prove. Because it runs against a real, shared Postgres instance rather than a disposable one, the test cleans up its own rows in an @AfterEach — a hygiene habit that matters once tests don't own a throwaway database.

Multi-stage Docker build

Dockerfile
# Stage 1: build — needs Maven + the full JDK
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline      # cached as its own Docker layer
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: run — only needs a JRE + the jar
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
Theory
A multi-stage build lets a Dockerfile use one image to build the artifact and a completely different, smaller image to run it — only the COPY --from=build line crosses between stages. The final image never contains Maven, the compiler, or the source tree — just a JRE (no compiler, smaller than a full JDK) and one jar file. mvn dependency:go-offline is placed before COPY src deliberately: Docker caches each instruction's layer, so as long as pom.xml hasn't changed, a rebuild reuses the downloaded-dependencies layer and only re-runs the (fast) compile step.

One jar, many environments — Spring profiles

application.properties hardcodes local defaults (a local Postgres, a dev JWT secret). application-docker.properties replaces every one of those with an ${ENV_VAR} placeholder, and is only loaded when SPRING_PROFILES_ACTIVE=docker is set — the mechanism docker-compose.yml and the Render deployment both use. Same jar, same code, different configuration source per place it runs.

The frontend contract

CORS · REST · Bearer tokens

Part 6's React app isn't Spring Boot, but it's the reason two of Spring's cross-cutting pieces exist at all.

Theory
Browsers enforce the same-origin policy: JavaScript running on ceylonpay.vercel.app is blocked by default from reading a response from ceylonpay-api.onrender.com — a different origin (scheme + host + port). CORS (Cross-Origin Resource Sharing) is the server opting back in: it returns headers naming exactly which origins, methods, and headers it will allow, and the browser enforces that answer.
config/SecurityConfig.java
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration configuration = new CorsConfiguration();
    configuration.setAllowedOrigins(allowedOrigins); // from cors.allowed-origins, env-configurable
    configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    configuration.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    // registered on the security filter chain via .cors(...)
}

On the client, the JWT never lives in a cookie — the React app stores it in localStorage and attaches it itself on every request: Authorization: Bearer <token>. That's a deliberate pairing with the stateless design in Part 2 — no cookie means no CSRF surface, but it also means the frontend, not the browser, is responsible for remembering and re-attaching the token.

Cross-cutting: turning exceptions into a stable API

@RestControllerAdvice

Every service throws plain, meaningful Java exceptions — InsufficientBalanceException, WalletNotFoundException — with no idea what HTTP status code means "insufficient balance". That translation happens in exactly one place.

Theory
@RestControllerAdvice is a cross-cutting concern — logic that would otherwise be duplicated in every controller (a try/catch around every method) is instead declared once, globally. Spring intercepts any exception a controller method throws, matches it against an @ExceptionHandler(SomeException.class) method here, and uses that method's return value as the actual HTTP response.
config/GlobalExceptionHandler.java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(InsufficientBalanceException.class)
    public ResponseEntity<Map<String, String>> handleInsufficientBalance(InsufficientBalanceException e) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(Map.of("error", e.getMessage()));
    }
    // one handler per exception type — WalletNotFound → 404, InvalidCredentials → 401, ...
}

This keeps the service layer's job pure — decide what went wrong and say so in a Java exception — and the web layer's job separate — translate that decision into the HTTP contract the frontend expects: always { "error": "..." }, always a status code chosen on purpose. The one gap the frontend build ran into (Part 6 of the React work): a @Valid failure on a request DTO throws Spring's own MethodArgumentNotValidException before a controller method body ever runs — not caught by any handler above — so that failure falls back to Spring's default, generically-shaped 400. Same mechanism, no handler registered for it here.
